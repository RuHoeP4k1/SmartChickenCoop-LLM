# RAG Hyperparameter Sweep — Experiment Documentation

This document describes the systematic experiment we ran to optimise the RAG pipeline.
It serves as both a reference for teammates and a source for the final report.

---

## 1. Why We Did This

Our RAG pipeline has many configuration choices that were set to reasonable defaults
but never validated:

- Which LLM to use (we only tested smollm2:1.7b)
- Which embedding model produces the best retrieval
- How many chunks to retrieve per query
- How large each chunk should be
- Whether hybrid retrieval (BM25 + semantic) beats pure semantic search
- Whether MMR diversity reranking helps or hurts

All of these affect answer quality. Instead of tuning them by gut feeling, we ran a
structured experiment using a **D-Optimal design** — a statistical technique from
Design of Experiments (DoE) that identifies which factors matter most and what the
optimal levels are, while using far fewer test runs than testing every combination.

---

## 2. Experiment Design

### 2.1 Parameter Space

| Factor | Symbol | Levels | Values Tested |
|--------|--------|--------|---------------|
| LLM model | A | 4 | smollm2:0.5b · smollm2:1.7b (baseline) · llama-3.1-8b · llama-3.3-70b |
| Embedding model | B | 2 | nomic-embed-text-v2-moe (baseline) · text-embedding-3-small |
| Chunk size | C | 3 | 400 · 600 · 800 characters |
| Retrieved chunks (k) | D | 3 | 2 · 4 · 6 |
| Hybrid weights | E | 2 | 50 % BM25 / 50 % semantic · pure semantic (0 / 100) |
| Search algorithm | F | 2 | MMR (Maximum Marginal Relevance) · cosine similarity |

**Full factorial size:** 4 × 2 × 3 × 3 × 2 × 2 = **288 configurations**

### 2.2 Design Method: D-Optimal

A D-Optimal design selects a subset of runs that maximises the determinant of the
information matrix (X′X). This gives the most precise estimates of all **main effects
and two-way interactions** with the fewest runs.

| Design | Runs needed | What it resolves |
|--------|-------------|-----------------|
| Full factorial | 288 | All effects + all interactions |
| Plackett-Burman | 12 | Main effects only |
| **D-Optimal (used)** | **~60** | Main effects + two-way interactions |

We chose D-Optimal because:
- Two-way interactions are expected (e.g. k only helps when chunks are small enough)
- 60 runs is feasible within our compute and API budget
- Results are still publishable and statistically interpretable

The design matrix is generated by `pyDOE3` and saved to
`evaluation/results/doe_design.md` before the sweep starts, so it can be
inspected and reported on independently of the results.

### 2.3 Evaluation: How Answers Are Scored

Each configuration is tested on **30 questions** from `evaluation_data.py` covering
8 categories: environment, general, health, behavior, housing, nutrition, seasonal, management.

Every answer is scored on two metrics by an **AI judge** (Gemini 2.0 Flash via OpenRouter,
free tier — chosen because it is a different model family from all tested LLMs):

| Metric | What it measures | Scale |
|--------|-----------------|-------|
| **Actionability** (GEval) | Does the answer tell the keeper what to do? | **1–3** |
| **Correctness** (GEval) | Is the chicken-keeping advice factually accurate? | **1–3** |
| **Faithfulness** | Answer is grounded in retrieved context (no hallucination) | 0–1 |
| **Answer Relevancy** | Answer actually addresses the question asked | 0–1 |
| **Contextual Precision** | Relevant chunks ranked before irrelevant ones | 0–1 |
| **Contextual Recall** | Retrieved context contains what's needed to answer | 0–1 |
| **Contextual Relevancy** | Retrieved chunks are relevant to the query | 0–1 |

Scoring criteria are defined in `eval_config.py` (written by the evaluation teammate).

A **combined score** (average of actionability + correctness) is used for ranking.

## 3. Two-Round Structure

### Round 1 — D-Optimal Sweep

Run all ~60 configs. Analyse with `sweep_analysis.py` to find:
- Which factors have the largest effect (ANOVA p-values)
- The top-performing configurations
- Whether small models fail on retrieval or generation (visible from answer text)

**Gate: Prompt Review**

Before Round 2, review the actual answer text from the best and worst configs.
Ask: is the failure mode the model, the retrieval, or the prompt phrasing?
Update `prompts.py` if needed. Tag the commit `prompt-v2`.

### Round 2 — Focused Confirmation

Fix low-impact factors at their best Round 1 level.
Run a full factorial on the 2–3 factors that ANOVA identifies as significant.
Compare the winner config with prompt-v1 and prompt-v2 to measure prompt impact.

## 5. Run Instructions

### Prerequisites

```bash
# Install sweep dependencies (on top of existing requirements)
pip install pyDOE3 langchain-openai scipy

# Pull the smaller local model (1.7b is already present)
ollama pull smollm2:0.5b
```

Add to your `.env` file:
```
OPENROUTER_API_KEY=sk-or-v1-...    # free at https://openrouter.ai
OPENAI_API_KEY=sk-...              # only needed for text-embedding-3-small variant
SWEEP_JUDGE_MODEL=google/gemini-2.0-flash-exp:free   # default, can omit
```

---

### Step 1 — Preview the design (no API calls)

```bash
python evaluation/sweep.py --dry-run
```

Prints the D-Optimal design matrix and exits.
Also saves `evaluation/results/doe_design.md`.

---

### Step 2 — Smoke test (fast, ~5 min)

```bash
python evaluation/sweep.py --n-questions 3 --n-runs 6
```

Runs 6 configs with 3 questions each (18 LLM calls + 36 judge calls).
Confirms API keys work and scoring is set up correctly.

---

### Step 3 — Full Round 1 sweep (~2–3 hours)

```bash
python evaluation/sweep.py
```

Runs all ~60 D-Optimal configs × 30 questions.
Saves checkpoint after every config — safe to interrupt with Ctrl+C and resume later:

```bash
python evaluation/sweep.py    # resumes automatically from checkpoint
```

To start fresh (ignore checkpoint):
```bash
python evaluation/sweep.py --fresh
```

Output: `evaluation/results/sweep_<timestamp>.json`

---

### Step 4 — Analyse results

```bash
python evaluation/sweep_analysis.py
```

Auto-loads the latest sweep results and produces:

**A. Main Effects Table** — average score per level per factor, sorted by impact range

**B. One-way ANOVA** — F-statistic and p-value per factor.
Factors with p < 0.05 are statistically significant (worth tuning in Round 2).

**C. Two-way Interaction Tables** — text heatmaps for all pairs of significant factors.
Example: "does k=6 only help when chunk_size=800?"

**D. Top 10 Configurations** — ranked by combined score

**E. Markdown report** — saved to `evaluation/results/round1_analysis.md`
(this file is the main output for the team review meeting)

Options:
```bash
# Focus on a specific metric
python evaluation/sweep_analysis.py --metric actionability
python evaluation/sweep_analysis.py --metric correctness

# Load a specific result file
python evaluation/sweep_analysis.py --input evaluation/results/sweep_20260310_143000.json

# Show more configurations in the ranked table
python evaluation/sweep_analysis.py --top 20
```

---

### Step 5 — Team review + prompt update

Read `evaluation/results/round1_analysis.md`.

Checklist:
- [ ] Which factors are significant (p < 0.05 in ANOVA)?
- [ ] What are the top 3 configs? What do they have in common?
- [ ] Read actual answer text from best/worst configs in the JSON
- [ ] Identify whether failure mode is model size, retrieval, or prompt phrasing
- [ ] Update `prompts.py` if needed — commit as `prompt-v2`

---

### Step 6 — Round 2

Fix low-impact factors. Run full factorial on the 2–3 significant factors:

```bash
# Example: only test LLM × chunk_size × k combinations (edited in sweep_config.py)
python evaluation/sweep.py --n-runs 36
python evaluation/sweep_analysis.py
```

Pick winner config. Update `.env.example` with the recommended production values.

---

### Step 7 — RAG vs no-RAG comparison (after Round 2)

Once the winner config is known, run the final head-to-head comparison:

```bash
python evaluation/evaluate_deepeval.py
```

This uses the **same winner LLM and retrieval settings** hardcoded in (or passed as args to) `evaluate_deepeval.py`.
It scores both conditions with the same 7 DeepEval metrics, so the comparison is directly comparable to sweep results.

**Why at the end:** running this earlier (with a suboptimal config) would understate RAG's benefit.
The no-RAG condition is the same LLM with `retrieval_context=[]` — no documents retrieved.

> **Note on RAGAS:** `evaluate_ragas.py` is not used in this evaluation plan.
> The 5 RAGAS metrics (Faithfulness, Answer Relevancy, Contextual Precision, Contextual Recall, Contextual Relevancy)
> are already collected by the sweep via DeepEval's standard RAG metrics — running RAGAS on top would be redundant.

---

## 6. What Changes Between Rounds

The only file changed between rounds is `prompts.py` (if the review identifies prompt issues).
No structural code changes — the sweep infrastructure is reused as-is.

| Between rounds | Action |
|---|---|
| Update prompt | Edit `prompts.py`, commit as `prompt-v2` |
| Narrow parameter space | Edit `PARAM_GRID` in `sweep_config.py` |
| Add human ranking | Merge CSV in `sweep_analysis.py` (future work) |

---

## 7. Notes for the Report

- **Design method:** D-Optimal, generated by `pyDOE3`, ~60 runs of 288 full factorial
- **Evaluation metric:** DeepEval — 2 G-Eval criteria (actionability, correctness, **1–3 scale**) + 5 standard RAG metrics (faithfulness, answer relevancy, contextual precision/recall/relevancy, **0–1 scale**)
- **AI judge:** Gemini 2.0 Flash (Google, free tier via OpenRouter) — not one of the tested models
- **Test set:** 30 questions, 8 categories, sensor data disabled (knowledge-only evaluation)
- **Statistical analysis:** One-way ANOVA per factor (scipy), two-way interaction tables for significant pairs
- **LLM backends:** smollm2 models run locally via Ollama; llama models via OpenRouter free tier

The design matrix (`doe_design.md`) and full results JSON are committed to the repo
alongside this document, so the experiment is fully reproducible.
